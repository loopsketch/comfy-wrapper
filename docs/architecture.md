# 構成と設計判断

なぜこの形になっているか。動かし方は [operations.md](operations.md)、モデルの選び方は
[models.md](models.md) にある。

## 全体の形

```
[client コンテナ]   手元。生成の投入と回収
  |  http://tunnel:8000 + Bearer <key>
  v
[tunnel コンテナ]   ssh -L (colab ssh --proxy-mode を ProxyCommand に)
  |
  |  ~~~ Colab ランタイム ~~~
  v
[FastAPI :8000]     認証・ジョブ管理・入力の受け渡し
     |  127.0.0.1 のみ
     v
[ComfyUI :8188]     ワークフローの実行
```

コンテナの中から見た宛先は `http://tunnel:8000`、ホストの `cw` から見た宛先は
`http://127.0.0.1:8000`。どちらもセッションをまたいでも変わらない。

## ComfyUI を外に出さない

ComfyUI には認証機構がない。これは実装漏れではなく設計方針で、公式の SECURITY.md に
「本番向けの認証はコアの範囲外」と明記されている。ワークフローを投げられること自体が
任意コード実行と等価なので、露出したインスタンスは実際に狙われている。2026年には
クリプトマイニングのボットネットのキャンペーンが動いた。

そこで ComfyUI は `127.0.0.1:8188` に閉じ、外に出るのは SSH トンネルを通した FastAPI
だけにしてある。ポート 8188 は公開しない。

## トンネルは ssh -L に落ち着いた

最初は cloudflared の quick tunnel を使っていた。動きはするが URL が起動のたびに変わり、
呼ぶ側の `.env` を毎回貼り替える必要があった。Colab CLI の `colab ssh` がポート
フォワードに対応していると分かったので、常駐の `ssh -L` を張る `tunnel` サービスへ
置き換えている。宛先が固定されたおかげで、呼ぶ側は設定を持たなくてよくなった。

トンネルだけが落ちることはある。そのときは `cw tunnel restart` でトンネルだけ張り直す。
確保し直すと生きているランタイムを捨てて GPU を取り直すことになるので、まずトンネルを疑う。

## キーは平文をランタイムへ送らない

`cw key issue` は手元でキーを作り、`.colab/comfy-keys.json` に保存する。ランタイムへ送るのは
SHA-256 のハッシュだけで、平文はどこにも上がらない。発行と送信 (`cw key push`) が
2段階になっているのはこのため。

呼ぶ側のプロジェクトごとに別のキーを発行しておくと、片方だけ失効させられる。
`.colab/colab-api-key` を共有してしまうと、1つ失効させた瞬間に全員が止まる。

## ジョブの記録は2か所にある

置き場所も寿命も違うので、混ぜないほうがいい。

| 記録 | 置き場所 | ランタイムを止めると |
|---|---|---|
| サーバ側のジョブ状態 | ランタイムのメモリ | 消える。回収前に止めると成果物ごと失う |
| 手元の投入記録 | リポジトリの `.colab/jobs/` | 残る。出力先を絶対パスで持つ |

手元の記録が絶対パスを持つのは、`cw image --out ./hero.png` を別のディレクトリで実行しても
`cw jobs` が正しい場所へ回収できるようにするため。呼ぶ側のプロジェクトには記録を作らない。

## ランタイムを止めると何が残るか

`/content` は消える。ウェイトは次回また取得することになるが、Colab の回線は速く、
40GB 前後の取得はおおむね5分から25分で終わる。その時間はそのまま GPU の課金になるので、
まとめて投げて落とす運用が前提になる。

| もの | 止めた後 |
|---|---|
| ウェイト (30から45GB) | 消える。次回また取得する |
| サーバ側のジョブ状態と未回収の成果物 | 消える |
| アクセスキー (`.colab/comfy-keys.json`) | 残る。手元にある |
| 手元の投入記録と生成済みのファイル | 残る |

ウェイトのキャッシュを Drive に置く手もある。ただし 40GB 前後の空きが要るうえ、読み込みが
HF から取り直すのと大差ないこともあって、あまり報われない。効くのは運用の方で、モデルの
ロードはセッションに1回なので、カットをまとめて投げれば1本あたりの待ちは大きく下がる。

## ホストには Python もライブラリも入れない

コンテナは3つとも `python:3.12-slim` で、CUDA も ComfyUI もホストには入らない。検証は
WSL2 上の Ubuntu 22.04 / Docker 26.0 / Compose v2.25 で行っているが、ホストの
ディストリビューションには依存しない。`docker compose` のサブコマンド形式を使うので、
v1 の `docker-compose` では動かない。

`cw` だけは例外で、ホストの Python (3.11以上) で動く。依存パッケージはなく、ffmpeg も
要らない。生成コマンドがホスト側で動くおかげで、`--ref ./ref.png` や `--out ./hero.png` が
カレントディレクトリ相対のまま通る。コンテナに閉じ込めるとパスの読み替えが要るので、
ここは分けている。

## モジュールの役割

`src/` からの相対パス。

| パス | 役割 |
|---|---|
| `cli/main.py` | `cw` のディスパッチ。生成は `scripts/` の `main()` をこのプロセスで呼び、運用は `*.sh` を叩く |
| `server/app.py` | FastAPI 本体。認証・ジョブ管理・ComfyUI への橋渡し |
| `server/{h3,wan,ltx,ltx25,image,post}_workflows.py` | ComfyUI API フォーマットのワークフロー生成 |
| `server/video_common.py` | モデル共通の寸法・尺の計算と、出力段の拡大 |
| `server/comfy.py` | ComfyUI クライアント(投入・ポーリング・回収) |
| `server/auth.py` | キーの発行・保存・検証(平文は保存しない) |
| `setup/download_*.py` | ウェイトの取得 |
| `scripts/colab.sh` | Colab CLI のラッパ(常駐コンテナ経由で叩く) |
| `scripts/colab_run.sh` | 確保 → 構築 → 実行 → 停止 を無人で1本流す |
| `scripts/colab_watch.sh` | 監視。keep-alive・進捗記録・自動停止・成果物の回収 |
| `scripts/measure_video.py` | 生成時間の測定(ロード込みとロード済みを分ける) |
| `lib/colab_link.py` | 手元側の共有層。宛先・キー・リトライ・障害の切り分け |
| `lib/mp4_probe.py` | mp4 のヘッダから寸法・fps・フレーム数を読む(ffmpeg 不要) |
| `lib/video_sizes.py` | 480p / 720p / 1080p をモデルごとの生成キャンバスと出力寸法に落とす |

`server/*_workflows.py` は ComfyUI 公式テンプレートのサブグラフを展開して API フォーマットに
落としたもので、ノード構成と入力名は公式実装に合わせてある。

## 同じマシンで2つ動かさない

OAuth トークンと SSH 鍵とセッション一覧は `.colab/` に1組しか持てない。リポジトリを複製して
両方から確保すると、`Already-active SSH session (HTTP 429)` を踏むか、片方のセッションが
アイドル刈り取りに巻き込まれる。2026-08-12 に実際に踏んだ。

呼ぶ側のプロジェクトに `colab` / `tunnel` サービスを持たせないこと。頼み方は
[operations.md](operations.md) の「他のプロジェクトから頼む」にある。
