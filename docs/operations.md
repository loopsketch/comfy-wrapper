# 運用ガイド

入れ方と最短の使い方は [README.ja.md](../README.ja.md) にある。ここは、GPU の課金を
止めながら回すための判断と手順。

## 課金の前提

Colab は生成の本数ではなく GPU の稼働時間で課金される。都度課金は 100CU = 1179円
(1CU = 11.79円)。

| GPU | CU/時 | 円/時 | VRAM | FP8 |
|---|---|---|---|---|
| L4 (既定) | 1.54 | 18.16 | 24GB | ネイティブ (sm89) |
| A100-SXM4 | 5.3 | 62.49 | 40GB | 非対応 (sm80) |

L4 を既定にしているのは、A100 の 3.44分の1 の単価に対して生成が 1.44倍しか遅くないから。
損益分岐は 3.44倍なので大きく余裕がある。根拠は [benchmarks.md](benchmarks.md)。

稼働時間で課金されるということは、確保したら必ず止める、ということに尽きる。止め忘れは
寝ている間も課金が続く。ウェイトの取得時間も課金されるので、カットはまとめて投げて落とす。
確保してから「次どうしますか」と相談している間も課金は進むので、どこまでやるかは確保の前に
決めておく。202 が返った投入を投げ直さないのも同じ理屈で、届いていれば生成は走っており、
投げ直したぶんの GPU 時間はそのまま捨てることになる。

## 標準の1セッション

```bash
cw status                                            # まず現状を見る
cw up --setup video --models ltx-2.5 --gpu L4 --max 60
cw video ./still.png --model ltx-2.5 --out ./clip.mp4
cw stop
```

`--setup` は `image`(静止画)、`video`(Wan2.2 と LTX)、`h3`(MiniMax H3)の3つ。`--max` は
監視の上限で、これを超えると監視がランタイムを止める。構築(ComfyUI の導入とウェイトの
取得)には15分から25分かかる。

`cw up` は返る直前に、手元から `/health` を1回叩いて経路が通っていることを確かめる。
落ちていればトンネルだけ張り直す(セッションは触らない)。直らなかったときは
`cw tunnel restart` を案内して終わるので、確保し直さずにそちらから復帰する。

構築したモデルと `--model` は必ず揃える。`--models` で入れたのは1モデルだけなのに
`cw image` の既定が `z-image` なので、うっかり既定のまま投げると ComfyUI が
`value_not_in_list` (400) で弾く。2026-08-12 に踏んだ。セッションは残るので投げ直せば
済むが、往復1分から2分ぶんの GPU を掴んだままになる。

## 確保した直後に確かめる

`--gpu L4` を渡して `colab new` が成功しても、実際には CPU の VM が返ってくることがある。
2026-08-12 には、それに気づかず 28GB のウェイトを CPU 機へ落としていた。

```bash
cw sessions      # Hardware: L4 / Variant: GPU を見る
```

`cw sessions` はローカルの記録ではなくサーバに問い合わせる。`cw status` の方は compose、
セッション、監視、疎通を1画面にまとめて出す。

## 監視の働き

`colab_watch.sh` は3つの仕事をする。keep-alive を維持し、進捗を
`.colab/keepalive-watch.log` に記録し、上限時間かアイドルでランタイムを止める。止める前に
成果物を回収する。

無進捗が続いたときの自動停止は実際に効いている。2026-08-12 に GitHub への clone が固まった
回では、ディスク使用量が 48.4GB から動かなくなった時点で8分の無進捗と判定され、自動停止した。
放っておけば上限60分まで回って18円になっていたところが3円で済んでいる。

逆に、動いているのに止めた回もある。2026-08-18 の qwen-image-edit で、取得が固まって素の
HTTP へ切り替えたとき、書きかけを捨てたのでディスクが 134.3GB から 53.7GB へ落ちた。当時の
判定は過去の最大を超えたときだけ進捗と見なしていたため、取り直しが 3.4GB まで伸びていても
「何も進んでいない」と数えていた。いまは減ったことも動いた証拠として扱い、そこを新しい基準に
して待ち直す。

長い構築を回すときは、監視を始めてから投げること。取得の遅さで63分かかった回に keep-alive が
落ち、成果ゼロで65円を使ったことがある。

## 止め方と確認

```bash
cw stop
```

監視 → セッション → サーバへの問い合わせ → トンネル、の順に畳む。最後にサーバの答えを出すのは、
ローカルの記録からセッションが消えることと、リモートのランタイムが止まることが別だから。
課金は GPU 時間なので、本当に消えたかどうかは自分の目で確かめてほしい。

最後の一覧に `[?]` で始まる名前なしのセッションが残っていたら、管理から外れた孤児で
`cw stop -s <名前>` では引けない。`cw stop --orphans` で解放する。名前つきも含めてすべて
外したいときは `src/scripts/colab_unassign.py --all` を直接叩くことになるが、一括で外すと
走っている GPU セッションまで巻き添えになるので、まず `--dry-run` で何が消えるかを見る。

トンネルを残さないこと。セッションがない状態でトンネルが動いていると、その ProxyCommand
(`colab ssh -s comfy`) がその名前でランタイムを確保してしまう。観測された限りでは CPU
ランタイムなので CU は減らないが、頼んでいない確保ではある。`cw stop` はトンネルも畳む。

## 無人で1本流す

`cw run` は確保 → 構築 → 実行 → 停止 を一息で流し、失敗しても必ず止める。`--` の後ろは
`client` コンテナの Python に渡されるので、そこだけはコンテナ内のパスで書く。

```bash
cw run --setup video --models ltx-2.5 --gpu L4 --max 60 -- \
  src/scripts/measure_video.py submit works/still.png --model ltx-2.5 --aspect 9x16
```

`cw up` との違いは終わり方だけで、`cw up` はセッションを残す。

## まとめて投げる

`POST /v1/generate` は 202 を返して裏で走る。モデルのロードはセッションに1回なので、
カットを全部投入してから回収するのが基本形になる。

```bash
cw image "..." --no-wait
cw image "..." --no-wait
cw jobs              # 投入済みをまとめて回収する
```

とはいえロードにかかるのは実測で50秒から70秒(モデルによる)で、まとめ投げの利きは思ったほど
大きくない。1本だけ回す回でも待ちが1分伸びるだけ、と読める。

## 他のプロジェクトから頼む

このリポジトリはマシンに1つだけ動かす。理由は [architecture.md](architecture.md) の
「同じマシンで2つ動かさない」にある。頼み方は2通りで、人が頼むなら `cw`、コードが頼むなら
HTTP になる。

人が頼む場合は、呼ぶ側のディレクトリでそのまま `cw` を叩く。生成物はそこに出て、記録とキーは
comfy-wrapper 側に残る。

```bash
cd /path/to/your-project
cw image "..." --out ./assets/hero.png
```

コードから頼む場合は、共有ネットワークに乗せて `http://tunnel:8000` を解決させる。呼ぶ側は
同じ宣言を繰り返すだけでよく、ホストにポートを開けなくて済む。

```yaml
services:
  app:
    networks: [default, comfy]
networks:
  comfy:
    name: comfy-net
```

`external: true` は付けない。まだ存在しない外部ネットワークを指定すると Compose が起動そのものに
失敗し、呼ぶ側は生成と関係ない作業もできなくなる。名前を固定して `external` を付けなければ、
先に上がった方が作って後から片方が参加する。

キーはプロジェクトごとに発行して、呼ぶ側の `.env` に置く。

```bash
cw key issue --name <project>    # 平文が出るのはここだけ
cw key push                      # ハッシュをランタイムへ送る
cw key list
cw key revoke --id <id>
```

モデルの表は写さずに `GET /v1/models` から読む。写しは新しいモデルが増えた瞬間に古くなる。
実際、このリポジトリが `ltx-2.5` に対応した後も、呼ぶ側が未知のモデルとして弾いていた。
ランタイムがないと `ready`(ウェイトが実際にあるか)だけ null になるが、カタログ自体は
ランタイムなしでも答える。見積もりは GPU を掴む前に要るので、呼ぶ側でキャッシュしておくとよい。

呼ぶ側が知っておく必要があるのは、投入が 202 で返って裏で走ること、ジョブの状態はサーバの
メモリにしかないこと、ランタイムの確保と停止はこのサーバの仕事であること。`/health` が
答えなければ、いま動いていないというだけ。

実例は [music-video-creator2](https://github.com/loopsketch/music-video-creator2) にある。
このリポジトリはそこから切り出したもの。

## テスト

```bash
python3 -m unittest discover -s tests -t tests                          # ホスト
docker compose run --rm client -m unittest discover -s tests -t tests   # コンテナ
```

両方通ることを確かめる。`cw` はホストの Python で動き、`docker compose run --rm client` は
コンテナの中で動くので、リポジトリルートの解決(`/app` かクローン先か)を間違えると片方だけが
壊れる。

GPU もランタイムもネットワークも要らない。カバーしているのは、気づかないまま GPU を掴んでから
初めて失敗するたぐいの間違いで、ワークフローのグラフ整合性、寸法とフレームグリッド、宛先と
キーの解決、リトライの方針(POST は再送しない)、ウェイト取得前の事前点検、止まった
ダウンロードの再起動、OAuth の更新、mp4 ヘッダの解釈が入っている。
