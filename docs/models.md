# モデルの選び方

1セッションに1モデル。どれも 30GB から 45GB あり、`/content` にも VRAM にも同時には
載らない。実測の数字は [benchmarks.md](benchmarks.md) にある。

`cw models` は同じ表をランタイム無しでも出す(「載っているか」だけ不明になる)。
呼ぶ側のコードは `GET /v1/models` から読むこと。

## 動画モデル

| model | ウェイト計 | 音声 | fps | 素の解像度 | タスク |
|---|---|---|---|---|---|
| `minimax-h3` (既定) | 42.5GB | あり | 24 | 短辺768・最大 768x1344 | t2v / i2v / 先頭・末尾 / 参照つき (r2v) |
| `wan2.2` (14B MoE) | 約38GB | なし | 16 | 832x480 / 1280x720 | t2v / i2v / 先頭・末尾 |
| `wan2.2-5b` (TI2V) | 約18GB | なし | 24 | 1280x704 | t2v / i2v |
| `wan2.2-s2v` (S2V 14B) | 約25GB | 入力を載せる | 16 | 832x480 | 音声で駆動 |
| `ltx-2.3` (22B fp8) | 約42GB | あり | 8から50 (既定25) | 1280x704 / 1920x1088 | t2v / i2v |
| `ltx-2.3-gguf` (Q4_K_M) | 約28GB | あり | 8から50 (既定25) | 同上 | t2v / i2v |
| `ltx-2.3-ic` (+IC-LoRA) | 約29GB | あり | 同上 | 同上 | i2v + 参照シート |
| `ltx-2.5` (22B int8) | 約40GB | あり | 8から50 (既定24) | 同上 | t2v / i2v / 先頭・末尾 |

迷ったときの目安。

- i2v をまとめて回すなら `ltx-2.3-gguf`。L4 で一番速く、音声つきで 25fps
- 先頭と末尾を指定したいなら `ltx-2.5` か `minimax-h3` か `wan2.2`
- 参照つき生成 (r2v) が要るなら `minimax-h3` だけ
- 音声で口や動きを駆動したいなら `wan2.2-s2v`

## L4 に載るか

ここだけはモデルで判断が変わる。

`wan2.2-5b` (10GB) と `wan2.2` (14.3GB を high / low で順に読む) は 24GB に収まる。
14B は前半と後半で別のウェイトを読むので、1本ごとにロードが1回挟まる。
`minimax-h3` は 21GB で収まる。

`ltx-2.3` の fp8 はチェックポイントだけで 29GB あり、L4 では部分オフロードに落ちる。
L4 で回すなら `ltx-2.3-gguf` (本体 14.2GB) を使い、fp8 は A100 に回す。

`ltx-2.5` は int8 (21.5GB) で L4 に載る。480p でも 720p でも `loaded partially` が
出ず、フルロードで回った (2026-08-17 実測、生成中の VRAM は 21.4/23.0GB)。bf16 は
42GB で1セッションに収まらず、nvfp4 (18.7GB) は Blackwell 専用なので Ada の L4 では
選べない。

GGUF は ComfyUI 本体だけでは読めない。`ltx-2.3-gguf` を選んだときだけ、構築が
[ComfyUI-GGUF](https://github.com/city96/ComfyUI-GGUF) を `custom_nodes` に入れる
(`UnetLoaderGGUF` がこれで生える)。fp8 のチェックポイントに同梱されていた VAE・
音声 VAE・接続子は、GGUF では別ファイルとして配られているものを使う。音声 VAE と
接続子は `checkpoints/` に置く。ComfyUI 側のローダが `ckpt_name` 入力から選ぶので、
`vae/` に置くと候補に出てこない。

## 尺はグリッドに切り上げられる

`duration` に指定した秒数は、モデルごとの latent フレームグリッドへ必ず切り上げられる。
実際の尺はレスポンスの `seconds` に出る。

| model | グリッド | 5秒の実尺 | 上限 |
|---|---|---|---|
| `minimax-h3` | 17k+5 (24fps) | 5.17秒 (124F) | 15.08秒 (362F) |
| `wan2.2` | 4k+1 (16fps) | 5.06秒 (81F) | 10.06秒 (161F) |
| `wan2.2-s2v` | 4k+1 (16fps) | 4.81秒 (77F) | 4.81秒 (1チャンク) |
| `wan2.2-5b` | 4k+1 (24fps) | 5.04秒 (121F) | 10.04秒 (241F) |
| `ltx-2.3` | 8k+1 (25fps) | 5.16秒 (129F) | 16.0秒 (401F) |
| `ltx-2.5` | 8k+1 (24fps) | 5.04秒 (121F) | 16.7秒 (401F) |

H3 で `duration: 2` を指定しても 5.17秒で生成される。学習レンジが 124 から 362 フレーム
だから。

## リップシンクの経路は2つ

`wan2.2-s2v` は音声を wav2vec2 で埋め込みにして駆動する。`audio` フィールドに base64 で
渡す。渡す画像は先頭フレームではなく見た目の参照で、構図はモデルが作り直す。出力には
駆動した音声がそのまま載る。1チャンク 77フレーム (16fps で 4.81秒) が上限で、それより
長い尺は前チャンクを引き継ぐループが要る(未実装)。音声エンコーダは英語音声で学習
されているので、日本語の歌唱は当たりが緩くなる。

`minimax-h3` の参照つき生成は、音声を `<Audio 1>` として参照に渡す。尺は 15秒まで取れる。

S2V は参照画像の構図をかなり強く引き継ぐ。「カメラ目線のバストアップで歌う」と書いても、
横向き全身の参照を渡すと横向きのまま歌った (2026-08-11)。寄りの絵が欲しければ、
寄りの参照画像を用意する方が早い。

## 参照の渡し方はモデルで違う

参照つき生成 (r2v) は H3 だけ。画像9枚・動画3本・音声3本まで受け取り、プロンプトからは
`<Picture 1>` / `<Video 1>` / `<Audio 1>` で名指しする。

LTX は「1枚の参照シート」にまとめる (`ltx-2.3-ic`)。キャラ・小物・場所を並べた1枚を
`ref_images[0]` に渡すと、IC-LoRA "Ingredients" がそれらの見た目を通しで保つ。H3 のように
9枚を別スロットへ渡す形ではなく、シートの中身はプロンプト側で「左が人物、右がカート」と
説明する。

狙いは、引いたときに初めて見える形を補うこと。先頭フレームだけを渡すと、画面外にあった
部分をモデルが作り話で埋める。2026-08-11 には、カメラが引いた後にショッピングカートの
カゴが消えて骨組みだけになった。

公式の IC テンプレートは 8step の単パスだが、こちらは2段構えのまま足している。単パスで
試したらカートの形は直った代わりにカメラが破綻し、後半で床に落ちて被写体が画面外へ出た
(2026-08-12)。構図を保っていたのは前半パスの方だった。

| L4 / 480p / 5.16秒 | カートの形 | カメラ | 時間 |
|---|---|---|---|
| 参照なし | 引くとカゴが消えて骨組みになる | 指示どおり後退 | 72秒 |
| シート + 単パス | 直る | 破綻(床に落ちて被写体が画面外) | 198秒 |
| シート + 2段構え | 最後まで保つ | 破綻しない | 160秒 |

シートの構図は出力の構図にも影響する。右パネルに側面図を置いたら、カメラが正面後退から
3/4 の側面寄りに移った。狙いの画角があるなら、シートの各パネルもその画角に寄せる方が素直。
参照フレームが latent に併走するぶん、生成は参照なしの 2.2倍かかる。

`ltx-2.5` にはまだ IC-LoRA の参照シートが無い。必要なら `ltx-2.3-ic` に留まる。

## 蒸留 LoRA

Wan の 4step 蒸留 LoRA は既定で入る (`lightning`)。20step が 4step になって実測で数倍
速くなる代わりに、動きは大人しくなる。決めカットで動きが足りないと感じたら
`lightning: false` で 20step / cfg 3.5 に戻す。

LTX-2.3 は公式テンプレートが蒸留 LoRA 前提(前半8step + 後半3step)なので、そのままの
構成にしてある。`ltx-2.3-gguf` は蒸留済みのウェイトなので蒸留 LoRA を積まない。

## H3 のウェイト

H3 の中でどれを落とすか。

| ファイル | サイズ | 用途 |
|---|---|---|
| `minimax_h3_fl2va_pruned_int8_convrot` | 21.0GB | t2v / i2v / 先頭・末尾フレーム |
| `minimax_h3_ref2va_pruned_int8_convrot` | 21.0GB | 参照つき生成(既定では落とさない) |
| `qwen3vl_32b_minimax_h3_nvfp4_awq` | 15.7GB | テキストエンコーダ |
| `minimax_h3_video_vae_fp16` | 5.2GB | 映像 VAE |
| `minimax_h3_audio_vae_fp32` | 0.6GB | 音声 VAE |

i2v で使うのは fl2va だけ。渡している `first_frame` は参照画像ではなく「動画のフレーム0
そのもの」で、キャンバスに引き伸ばして keyframe として固定される。静止画を動かす i2v は
これで足りる。

ref2va が要るのは、画像をフレームではなく参照として使いたいときだけ。歌唱リップシンク、
キャラの同一性を動画生成側で押さえたいとき、既存クリップの動きを真似させたいときが該当する。

fl2va だけなら 42.5GB、ref2va も入れると 63.5GB。フル精度は 123.6GB あるので、Colab で
回すなら pruned + int8 が現実的な下限になる。fl2va と ref2va は 21GB ずつあって A100 の
40GB にも同時には載らないので、交互に呼ばずタスク単位でまとめて投げる。

量子化は int8 が既定。fp8 のウェイトもあるが、A100 (sm80) は FP8 演算をネイティブに
実行できないので、Ada 世代以外では int8 の方が素直に速い。L4 は Ada なので fp8 が効く。
上書きは `H3_FL2VA_MODEL` / `H3_REF2VA_MODEL` / `H3_TEXT_ENCODER` の環境変数で行う。

## 静止画モデル

| model | サイズ | 特徴 |
|---|---|---|
| `z-image` (Turbo) | 11.3GB | 速くて素直。参照画像は渡せない |
| `qwen-image` (2512) | 28.0GB | プロンプト追従が一段上。書き込み量が多い |
| `qwen-image-edit` (2511) | +20.7GB | 参照画像を渡せる。キャラの一貫性を絵で縛れる |

決定的な差は参照画像を渡せるかどうか。Z-Image には手段が無いので、キャラの一貫性を絵で
縛れるのは Qwen-Image-Edit だけになる。しかもかなり強く、正面立ちのシート1枚から公園の
ベンチに座る三分の四ビューを起こしても、顔・髪型・服装がスニーカーの赤ラインまで保たれた。
実写シートからアニメ版シートを起こす使い方もできる。

日本語の描画は Z-Image で 4文字中 3.75文字が正確、Qwen も同程度。アニメ調は両方とも
LoRA 無しで十分な品質が出る。LoRA は画風を寄せたいときの選択肢。

ディスクの都合で H3 (動画) と Qwen 系 (画像) は同居できない。Z-Image だけは同居できる。

配布元が Comfy-Org でないときは、ファイル名で ComfyUI 対応を確かめる。
`lightx2v/Qwen-Image-2512-Lightning` から int8 版を選んだら全面ノイズになり、同じ repo の
`..._comfyui_4steps_...` が正解だった。Comfy-Org の配布は `int8_convrot` のように
ComfyUI 対応が命名で明示されている。

## 解像度と拡大

H3 が生成できるキャンバスは短辺 768px・最大 768x1344 が上限で、これは変えられない。
`megapixels` から実サイズへの計算は ComfyUI の `ResolutionSelector` と同じで、1メガピクセルは
1e6 ではなく 1024x1024、幅と高さはそれぞれ独立に 32 の倍数へ丸められる。

| megapixels | 16:9 | 9:16 |
|---|---|---|
| 0.2 | 608x352 | 352x608 |
| 0.4 (既定) | 864x480 | 480x864 |
| 0.9 | 1280x736 | 736x1280 |
| 0.98 (ネイティブ上限) | 1344x768 | 768x1344 |

1344x768 は 1.75:1 で 16:9 ちょうどではないため、編集タイムラインに載せる素材としては
半端になる。そこで生成はネイティブ上限で行い、出力段で目標サイズちょうどに揃える2段構えに
してある。`output_width` / `output_height` を指定すると、ComfyUI 内で VAEDecode と
CreateVideo の間に拡大が挟まり、アスペクト差は center crop で吸収される。

| `resolution` | 生成キャンバス (16:9) | 最終出力 (16:9) | 最終出力 (9:16) |
|---|---|---|---|
| `480p` | 864x480 | 854x480 | 480x854 |
| `720p` | 1280x736 | 1280x720 | 720x1280 |
| `1080p` | 1344x768 | 1920x1080 | 1080x1920 |

拡大は lanczos が既定で、モデルは要らない。`upscale_model` に `upscale_models/` の
ファイル名を渡すと RealESRGAN などを通せるが、1080p 出力が目的なら勧めない。静止画用の
超解像はフレームごとに独立して推論するため時間的一貫性が無く、髪や布が毎フレーム違う形で
復元されてちらつく。劣化した実写の復元向けに学習されているので、既にクリーンな出力には
過剰にシャープを掛ける。1344x768 から 1920x1080 は 1.43倍で、x2 モデルだと 2688x1536 まで
上げてから縮めることになり、効果が打ち消される一方で中間テンソルだけ4倍に膨らむ。

拡大は情報量を増やさない。精細さが要るカットは、拡大方法をいじるより `megapixels` を
上げて生成解像度そのものを上げる方が効く。ただし H3 は 0.98MP を超えると学習範囲を
外れて構図が破綻しうるので、カット単位で確かめる。

メモリは「フレーム数 x 拡大後の画素数」で効く。1344x768 を 1920x1080 にする程度なら
5秒 (124フレーム) で約 3GB、15秒 (362フレーム) で約 9GB の中間テンソルになる。
4倍のモデル拡大を長尺に掛けると A100 でも詰まるので、倍率と尺はセットで考える。
